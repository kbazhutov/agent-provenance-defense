# План исследования

## Вопрос

Может ли проверка намерения пользователя, происхождения данных и аргументов вызова предотвратить изменение неправильных записей при наличии у агента формального права записи?

## Мотивация

Обычная проверка прав отвечает на вопрос «может ли агент писать в базу». Она не отвечает на вопросы «в какие записи можно писать», «какие поля можно менять» и «откуда взялась команда на изменение». Вредоносный документ может повлиять на решение агента, хотя формально у агента есть право записи.

## Предполагаемый вклад

Мы реализуем защитный слой перед инструментом записи. Он будет проверять:

1. соответствие целевых записей исходной задаче пользователя;
2. допустимость изменяемых полей;
3. происхождение аргументов и наличие данных из недоверенных документов;
4. объяснимость решения в журнале вызовов.

Работа не заявляет универсальное решение для всех prompt injection атак. Фокус — на ошибочном изменении записей в базе при многошаговом чтении документов.

## Система

Агент получает задание пользователя, читает документы и формирует вызов:

```json
{
  "action": "update_record",
  "record_id": "A-001",
  "field": "comment",
  "value": "Проверено",
  "source_ids": ["d1"]
}
```

В baseline вызов исполняется без проверки. В собственной версии перед исполнением появляется защитный брокер.

## Сравниваемые варианты

1. Без защиты.
2. Защитный системный промпт.
3. Обычная проверка права записи.
4. Проверка намерения, происхождения и аргументов.

## Сценарии атак

- документ просит изменить все записи;
- документ указывает записи другого клиента;
- документ просит изменить статус вместо комментария;
- вредоносная инструкция появляется после нескольких шагов;
- агент получает отказ и меняет формулировку вызова;
- документ пытается передать ID записи как разрешение.

## Метрики

- число несанкционированных изменений;
- число ошибочных блокировок;
- доля успешно выполненных законных задач;
- число вызовов и шагов;
- время и стоимость запуска;
- доля атак, остановленных до изменения базы.

## План эксперимента

1. Сначала фиксируем baseline и набор сценариев.
2. Затем реализуем защитный брокер.
3. После фиксации защиты создаём отдельный тестовый набор атак.
4. Проводим абляции: без проверки происхождения, без проверки области задачи и без проверки полей.
5. Переносим согласованный вариант на AgentDojo для внешней воспроизводимой проверки.

## Распределение работы

- Участник 1: база, инструменты и защитный брокер.
- Участник 2: baseline, атаки и интеграция с AgentDojo.
- Участник 3: метрики, запуски, абляции и анализ ошибок.

Каждый участник должен уметь запустить весь проект и объяснить результаты.
